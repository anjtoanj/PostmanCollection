# To configure Newman to fail a pipeline based on response time or error rate thresholds, you need to add assertions in Postman and use Newman exit codes to propagate failures to CI/CD.

1. Add Assertions in Postman

Use the Tests tab for each request (or globally in Collection / Folder).

Example: Fail if Response Time > 500 ms
pm.test("Response time is under 500ms", function () {
    pm.expect(pm.response.responseTime).to.be.below(500);
});

Example: Fail if Status Code is Not 2xx
pm.test("Status code is 2xx", function () {
    pm.expect(pm.response.code).to.be.within(200, 299);
});

2. Calculate Error Rate

Add a global counter for failed requests in a Pre-request or Tests script.

Collection-Level Pre-request Script
if (!pm.globals.get("failedCount")) {
    pm.globals.set("failedCount", 0);
}

Request-Level Test
if (!pm.response.code.toString().startsWith("2")) {
    let count = parseInt(pm.globals.get("failedCount")) + 1;
    pm.globals.set("failedCount", count);
}

3. Final Check (Postman Collection Level)

At the end of collection (in a separate request or Tests tab of last request):

let totalRequests = pm.info.iterationCount * pm.info.requestCount;
let failed = parseInt(pm.globals.get("failedCount"));
let errorRate = (failed / totalRequests) * 100;

pm.test("Error rate should be less than 1%", function () {
    pm.expect(errorRate).to.be.below(1);
});

4. Newman Exit Codes

Newman exits with:

0 → All tests passed

1 → Any test failed

CI/CD pipeline will fail if Newman exits with 1.

5. Azure DevOps Pipeline Example
- script: |
    newman run CatAPI_Performance_Test.json \
      -e CatAPI_Env.json \
      --iteration-count 100 \
      --reporters cli,html \
      --reporter-html-export newman/report.html
  displayName: 'Run API Performance Tests'
  continueOnError: false


continueOnError: false ensures the pipeline fails if Newman exit code is 1.

### Added Newman exit codes to fail the pipeline if average response time exceeded limits or error rate was above 1%. How to do this? ###
Newman does not natively support global thresholds, but you can enforce them using Postman assertions + Newman exit codes or a custom reporter.

1. Using Postman Assertions (Recommended)
A. Set Threshold Checks in Postman Tests
Check Response Time
pm.test("Response time is under 500ms", function () {
    pm.expect(pm.response.responseTime).to.be.below(500);
});

Track Failed Requests (for Error Rate)

In the Collection Pre-request Script:

if (!pm.globals.get("failedCount")) {
    pm.globals.set("failedCount", 0);
}
if (!pm.globals.get("totalCount")) {
    pm.globals.set("totalCount", 0);
}

In the Tests Tab of Each Request:

// Increment total requests
let total = parseInt(pm.globals.get("totalCount")) + 1;
pm.globals.set("totalCount", total);

// Check for errors (non-2xx)
if (pm.response.code < 200 || pm.response.code >= 300) {
    let failed = parseInt(pm.globals.get("failedCount")) + 1;
    pm.globals.set("failedCount", failed);
}

Final Check – Error Rate
At the last request or a dedicated “Check Thresholds” request:

let failed = parseInt(pm.globals.get("failedCount"));
let total = parseInt(pm.globals.get("totalCount"));
let errorRate = (failed / total) * 100;

pm.test("Error rate is below 1%", function () {
    pm.expect(errorRate).to.be.below(1);
});

B. Pipeline Failure Trigger
Newman exits with code 1 if any test fails.
Azure DevOps pipeline stops because continueOnError: false (default).

Common Issues Detected in Load Testing

1. Performance Bottlenecks
Slow API Response Times – APIs take longer than acceptable SLAs (e.g., >500 ms).
Database Query Latency – Poorly optimized queries causing delays.
Inefficient Code Execution – Loops, synchronous calls, or blocking operations.

2. Resource Utilization Problems
High CPU Usage – Spikes leading to throttling or service degradation.
Memory Leaks – Gradual memory usage increase leading to crashes.
Disk I/O Bottlenecks – Slow read/write impacting performance.
Network Bandwidth Saturation – High load saturating available network capacity.

3. Concurrency and Scalability Issues
Thread Locking or Deadlocks – Multiple processes waiting indefinitely.

4. Throughput Limitations
Requests per Second (RPS) Plateau – System unable to go beyond a specific throughput.
Queue Build-ups – Background processes or message queues lagging under heavy load.

5. Error Rate Spikes
HTTP 500 / 503 Errors – Server unable to handle request load.
Timeouts & Connection Failures – APIs dropping connections under stress.
Data Integrity Issues – Partial transactions or inconsistent database states.

6. Infrastructure Misconfigurations
Load Balancer Limits – Incorrect configuration leading to uneven load distribution.
Caching Issues – Missed caching opportunities causing excessive database hits.
API Gateway Throttling – Rate-limiting policies triggering prematurely.

7. Endurance & Soak Test Failures
Performance Degradation Over Time – System slows down or crashes during prolonged usage.
Memory Bloat & Garbage Collection Delays – Increasing response times during long runs.

How to Explain in Interview
“In load testing, we focus on uncovering performance bottlenecks, resource utilization issues, concurrency limitations, and error spikes under stress. 
For example, in one project, load testing helped us identify a memory leak that caused performance degradation after 4 hours of sustained usage.
We captured response times, throughput, CPU/memory usage, and error rates to analyze system behavior and implemented optimizations to meet SLAs.”
